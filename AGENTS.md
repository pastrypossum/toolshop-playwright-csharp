# AGENTS.md

## Scope and Intent
- This repository is a **tests-only** C#/.NET project for E2E UI automation against `https://practicesoftwaretesting.com` (no production code — a single NUnit test project, no `src/`).
- Primary flow: NUnit `[TestFixture]` test classes -> page objects -> Playwright browser/page (`ToolshopTest` base class) -> Allure results in `bin/{Configuration}/{TFM}/allure-results`.
- Same app under test as the sibling `toolshop-playwright-java` and `toolshop-playwright-typescript` projects; this project is newer and intentionally smaller in scope (it ports the contact-support flow and basic catalog search, not the full feature set the other two cover).

## Project Map (read these first)
- Build/test config: `Toolshop.Playwright.Tests.csproj`
- AI/project conventions: `.claude/skills/*/SKILL.md` (page-object, test, test-data, allure, api-helper, playwright-cli)
- Base test fixture (base URL + `data-test` attribute wiring): `Fixtures/ToolshopTest.cs`
- Page objects: `Pages/NavBar.cs`, `Pages/ContactPage.cs`, `Pages/ProductListPage.cs`
- Test suites: `Tests/AcceptanceTests/{Contact,Catalog}/*.cs` (UI, derive from `ToolshopTest`, `[AllureEpic("AcceptanceTests")]` + `[AllureFeature(...)]` — requirement-based, so it's on the Behaviors axis); `Tests/ContractTests/Brand/*.cs` (API contract tests for all `/brands*` endpoints, `[AllureParentSuite("ContractTests")]` + `[AllureSuite("Brand")]` + `[AllureSubSuite("{ClassName}")]`, one `SubSuite` per file — technical/lower-level, so it's on the Suites axis, and the file-level node matches `[assembly: Parallelizable(ParallelScope.Fixtures)]`'s unit of execution (one worker per file)). One file per resource per track, per `.claude/skills/contract-testing/SKILL.md`: `BrandSpecTests.cs` checks every operation against its OpenAPI spec, including gaps found between the spec and live behavior (e.g. `POST`/`PUT` accept no auth though the spec is silent on it, `DELETE` genuinely enforces `apiAuth`, and a `DELETE` on an in-use brand returns an undocumented `{"success":false,"message":"..."}` shape); `BrandPactTests.cs` checks real consumer dependencies traced from `practice-software-testing` source, not the spec (a brand `id` used to filter `GET /products`; the admin UI's error renderer expects field-keyed validation errors). `BrandAuthGapSpecTests.cs` is a separate file by design — deliberately red, tracking a known security gap, kept out of the main spec file so it stays all-green. `BrandContractTestBase.cs` holds the shared login/throwaway-brand/teardown helpers all of the above use. See `.claude/skills/allure/SKILL.md` for the Allure-axis rule.
- Test data: `Data/Contact/ContactMessageFactory.cs` (Bogus), `Data/Contact/ContactMessages.cs` (static strings), `Data/Fixtures/` (upload fixtures)
- Allure config: `allureConfig.json`

## Execution Workflow (non-obvious details)
- Use `dotnet test` for normal runs — there is no separate unit/integration test split (contrast with Java's Surefire/Failsafe split); every test here is a Playwright E2E test.
- Playwright's browser binaries are **not** restored by `dotnet restore`/`build` alone the first time: run `pwsh bin/Debug/net10.0/playwright.ps1 install chromium` once after the first build (the script is generated by the `Microsoft.Playwright` package's build target).
- `BASE_URL` (UI tests, defaults to the live site) and `API_URL` (contract tests, defaults to the local dev stack at `http://localhost:8091` so they exercise a disposable local database rather than mutating the public demo) can each be overridden independently, mirroring the TypeScript project's `playwright.config.ts`. `HEADED=1` and `BROWSER=<name>` are honored automatically by `Microsoft.Playwright.NUnit`'s default launch options — no code in this project overrides them.
- Allure results land under `bin/Debug/net10.0/allure-results/` (path depends on build configuration/TFM), not a fixed `target/`-style directory — see `allureConfig.json`.
- Parallelism is configured in `AssemblyInfo.cs`: `[assembly: Parallelizable(ParallelScope.All)]` + `[assembly: LevelOfParallelism(8)]` (contrast with Java's `junit-platform.properties` class-level concurrency). `[assembly: FixtureLifeCycle(LifeCycle.InstancePerTestCase)]` is mandatory alongside it — without it, NUnit shares one fixture instance across all of a class's `[Test]` methods, which is fatal once they run concurrently (every UI/contract test holds its own `Page`/`ApiContext` in instance fields). `Fixtures/ToolshopTest.cs` overrides back to `[Parallelizable(ParallelScope.None)]` for all UI tests specifically — launching several real Chromium instances at once against the single local Angular dev server proved genuinely unreliable (`TimeoutException`, not a correctness bug; verified stable across repeated runs both before and after this change). Contract tests (`Fixtures/ApiTest.cs`) have no such constraint and run with full 8-way parallelism. Every test must be independent and order-free per `.claude/skills/contract-testing/SKILL.md`'s Key Implementation Directives — own its data, own its cleanup, never assume another test's state.

## Test and Page-Object Patterns
- Every UI test fixture class derives from `Fixtures.ToolshopTest` (not `Microsoft.Playwright.NUnit.PageTest` directly) to inherit the base URL and `data-test` attribute configuration. Pure API contract tests derive from `Fixtures.ApiTest` instead (no browser launched) — see `Tests/ContractTests/`.
- Page objects are constructed with `new {Page}(Page)` in `[SetUp]`, stored in private fields, and used by every `[Test]` in the fixture — see `test.instructions.md`.
- `Page.GetByTestId(...)` is the default locator strategy; it only resolves against this app's `data-test` attribute because `ToolshopTest` calls `Playwright.Selectors.SetTestIdAttribute("data-test")` — see `page-object.instructions.md`.
- Allure reporting is applied via attributes (`[AllureNUnit]`, `[AllureSuite]`, `[AllureName]`) from `Allure.Net.Commons.Attributes`/`Allure.NUnit`, not a runtime API like the TS project's `allure-js-commons` — see `allure.instructions.md`.
- Dynamic test data comes from `Bogus` factories returning C# `record`s; fixed strings (error/success copy) are `const string` fields on a static class — see `test-data.instructions.md`.

## Integration Points and Data
- The app's base URL and the app's `data-test` attribute are centralised in `Fixtures/ToolshopTest.cs` — never hardcode `https://practicesoftwaretesting.com` in a test or page object.
- File upload fixtures live in `Data/Fixtures/` and must be referenced via `AppContext.BaseDirectory` (see `test-data.instructions.md`) — they are marked `CopyToOutputDirectory` in the `.csproj` so they exist next to the test binaries.
- There is no API helper layer yet (contrast with Java's `fixtures/APIAuth.java`/TS's `helpers/api/*.api.ts`) — when one becomes necessary it belongs at `Fixtures/APIHelper.cs`, alongside `ToolshopTest`, not a separate top-level folder — see `api-helper.instructions.md`.

## Agent Working Rules for This Repo
- Add new UI tests under `Tests/AcceptanceTests/{Area}/` as NUnit `[TestFixture]` classes deriving from `ToolshopTest`, or they won't get the base URL/test-id wiring. Add new contract tests under `Tests/ContractTests/{Resource}/`, one `{Resource}SpecTests.cs`/`{Resource}PactTests.cs` file per resource, deriving from `ApiTest`/`{Resource}ContractTestBase` — see `.claude/skills/contract-testing/SKILL.md`.
- Reuse or extend existing page objects in `Pages/` before adding raw `Page.Locator(...)` calls to a test.
- When adding a test, apply `[AllureNUnit]` + the correct axis for the test kind (`[AllureEpic]`+`[AllureFeature]` for UI, `[AllureParentSuite]`+`[AllureSuite]`+`[AllureSubSuite]` for contract tests) on the fixture and `[AllureName("...")]` on every `[Test]` method — a fixture without `[AllureNUnit]` silently produces no Allure results. See `.claude/skills/allure/SKILL.md`.
- New test resources (binary fixtures) go under `Data/Fixtures/` and must be added to the `<None Update="Data\Fixtures\**">` item group in the `.csproj` (a glob already covers the directory, but double-check new extensions aren't excluded elsewhere) so they copy to the output directory.
- Keep this project's scope honest: if a sibling project's test doesn't have a real C# equivalent yet, don't invent one just to match file-for-file — port behavior, not line count.
